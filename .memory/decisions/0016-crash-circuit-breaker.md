# 0016 — 同一执行方法连续崩溃两次后熔断

Status: Accepted
Date: 2026-07-27
Owners: project owner

## Context

Harness 在受限 macOS 环境中为多个 artifact 和 viewport 重复启动 Chrome。Chrome
在完成页面渲染前于应用注册阶段触发 `SIGABRT`，但执行流程仍继续使用相同参数启动
后续进程，因而制造了多份等价的系统崩溃报告，没有增加有效证据。

进程崩溃不同于普通命令失败。连续重试可能影响用户正在使用的应用、污染诊断记录，
也可能放大宿主环境中的故障。

## Decision

- 对同一执行对象使用实质相同的方法连续造成两次进程崩溃后，立即打开熔断器。
- 第二次连续崩溃是最后一次允许的同方法尝试；第三次及以后不得再按原方法启动。
- “同一方法”包括相同的程序、运行环境、权限边界和关键启动参数。只更换输入文件、
  viewport、输出路径、临时目录或重试编号，不视为更换方法。
- 熔断后必须：
  1. 停止该方法在当前 batch 中的剩余尝试；
  2. 保存退出信号、有限的标准错误、启动参数摘要和已生成的诊断文件引用；
  3. 将相关结果明确标记为 `partial`、`indeterminate` 或对应失败状态；
  4. 在再次执行前，先完成诊断并实质改变方法或运行条件。
- 可以解除熔断的实质变化包括：修复代码或参数、换用独立 headless runtime、切换到
  已获授权且不受原限制的运行环境，或完成能够证明根因已移除的 preflight。
- 用户明确要求继续，也不等于可以原样重试；必须向用户披露已有两次崩溃和拟采用的
  新方法。
- 本规则适用于 Chrome，也适用于 Pi、Docker、测试子进程及后续接入的外部工具。

## Alternatives considered

- 允许固定次数的普通重试：适合瞬时错误，但不能区分可恢复失败和进程级崩溃。
- 第三次崩溃后才停止：会多制造一次没有新信息的崩溃，因此不采用。
- 只为 Chrome 增加例外：范围过窄，无法保护其他子进程和宿主工具。

## Consequences

- 批处理可能在部分结果后提前停止，但静态分析和已有证据仍应保留。
- 执行器需要共享或集中维护 batch 内的连续崩溃状态，不能让每个输入独立地无限
  重试。
- 后续 Chrome 截图实现需要启动 preflight、有限 stderr 记录和 batch 级熔断，
  当前尚未实现。

## Revisit when

当框架拥有隔离且可丢弃的执行环境，并能证明崩溃不会影响用户应用或宿主系统时，
可以按工具类型调整阈值；默认阈值仍为两次。
