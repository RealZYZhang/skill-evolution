一句话说明

当前程序可以让同一个 skill 重复执行，保存每次执行的完整过程，比较不同 结果之间的差异，并在安全 Harness 通过后让四个独立 agent 查找跨 trajectory 模式。汇总、修改副本和发布仍属于未来另行批准的阶段。

这个 MVP 要解决什么问题

问题一

只看最终文件，不知道中间发生了什么

一个 HTML 可能最后生成成功，但模型之前可能写入失败、重复读取、返工， 或使用了很昂贵的方法。只保存最终文件会漏掉这些信息。

问题二

同一个 skill 每次结果可能差很多

单次成功不能证明执行方法稳定。需要重复运行，才能看到结构、内容、 样式、时间和 token 使用是否一致。

问题三

发现差异后，容易直接猜原因

程序先提取可核对的事实，再让 agent 回到具体执行步骤和文件位置分析， 避免把猜测写成结论。

问题四

修改 skill 后，容易覆盖原版本

所有修改先发生在完整副本中。原 skill 不动，修改内容和测试结果全部 保留，最后由人决定是否发布。

从执行到发布的完整过程

这些步骤彼此分开。收集执行记录时不做分析；分析证据时不直接修改 skill； 测试修改副本时也不会自动发布。

  1. 定义一次任务
  2. 重复执行
  3. 保存全过程
  4. 统计并比较
  5. 分工查问题
  6. 测试修改副本
  7. 人工决定发布

为什么要分开： 即使分析 agent 失败、修改方案无效或自动测试没有结论，之前的执行记录 仍然完整存在，不会被后续步骤改写。

各部分做了什么，目的是什么

1
已经写好并测试

任务说明

每次测试都要说明输入是文件还是粘贴文字、原文件名是什么、预期生成 哪些文件，以及本次测试关注什么能力。

目的： 让不同运行使用同一份明确要求，并保留 PDF、DOCX、TXT 等真实格式， 不把所有输入都假装成 Markdown。

2
已有真实运行记录

重复执行

给定一个 skill 和次数 N，程序会执行 N 次。每次运行都有自己的文件夹， 一次失败不会覆盖其他运行，也不会让失败记录消失。

目的： 观察同一个 skill 是否稳定，而不是用一次偶然成功代表整体表现。

3
已经写好并测试

执行过程记录

程序按发生顺序保存完整消息、工具调用、工具结果、失败、重试、运行配置、 最终结果和产物。Pi 正常结束时还保存它自己的 session。

目的： 能够回答“模型具体做了什么”“从哪一步开始返工”“失败后如何恢复”， 而不只看到最终文件。

4
已有真实报告

执行过程统计

程序统计调用次数、输入和输出 token、费用、耗时、工具动作、失败、 重试、重复读取、临时脚本、分段写入、合并和返工。

目的： 找到成本差异和低效步骤。统计使用每次调用的真实增量，不重复累计模型 返回的总 token。

5
静态比较完成，截图缺失

HTML 结果比较

程序比较标题、章节、链接、表格、无障碍标记、CSS 变量、颜色、字体、 脚本规模和可见文字，并列出每两个 HTML 之间的差异。

目的： 把“这五个页面看起来差很多”变成可核对的结构和内容事实。它不自动给 页面打总分，也不擅自选出“最好”的一个。

6
已经写好并测试

冻结完整研究语料

程序按目标检查样本，再冻结完整脱敏 trajectory、可读产物、单 trajectory 报告、 导航索引和统一基线。索引只帮助定位，不替 agent 预先总结结论。

目的： 保留摘要会遗漏的临时脚本和隐式行为，并让每条结论都能回到原 trajectory。

7
内部流程就绪，待验收与审批

先验证研究能力，再分工分析

无模型 Harness 先证明搜索、下钻、代码执行和正式提交都可用；随后两个 全新 session 独立盲测。两次都通过后，四个 agent 分别研究行为模式、 条件与覆盖、一致性和资源效率，结果暂不汇总。

目的： 先区分环境问题和 agent 能力问题，再让每个视角独立留下证据与失败记录。

8
未来阶段，尚未授权

证据不足时规划补采

当前系统只返回明确的缺失样本和补采要求，不会自动启动补测、Synthesis 或新的模型任务。未来如需补证流程，必须重新设计并由负责人批准。

目的： 不把样本不足伪装成结论，也不在未授权时扩大真实模型调用范围。

9
既有组件，当前研究不自动调用

制作修改副本

每个明确的问题只生成一个修改方案。程序复制完整 skill，在副本中修改， 再自行计算文件增删改和文字差异。

目的： 保护原 skill，并能准确回答改了什么。Agent 自己声称的差异不被当成事实， 以程序计算的结果为准。

10
既有组件，当前研究不自动调用

原版本与修改版本重新测试

修改版本先运行一次小测试；可以运行后，再让原版本和修改版本交替执行 同样的任务。默认一个方案最多安排 13 次运行。

目的： 用新的、成对的测试判断修改是否有效，避免拿不同时间、不同任务的旧记录 硬做比较。

11
未来阶段，尚未授权

独立判断测试效果

一个没有参与修改的 agent 查看原版本和修改版本的结果，分别说明哪些 方面变好、变差、好坏并存、证据不足或根本无法运行。

目的： 不把多个指标压成一个分数。正确性和能力覆盖不能用少花 token 来抵消。

12
未来正式报告阶段

人工发布决定

最终材料必须说明原 skill 是什么、执行记录是什么样、发现了什么问题、 修改长什么样，以及为什么认为修改可行或不可行。

目的： 自动检查不能隐藏失败方案，也不能直接发布。所有方案和测试结果都交给人 审阅。

已经实际验证了什么

  • 文档可视化 skill 已真实运行五次，每次都有独立执行记录、session 和 HTML 产物。
  • 五次运行的第一次完整文件写入都失败了；后续分别使用分段写入、临时 Python 生成器、重新生成、分片和合并等方法恢复。
  • 执行统计程序成功读取五次记录，并整理了资源使用和操作方法差异。
  • HTML 比较程序完成了 5 个产物的静态检查和 10 组两两比较。
  • 五条同版本成功 trajectory 已冻结为内部 smoke 语料；批次仍为 prepared，没有 Harness 通过记录、AgentRun、能力认证、Specialist 结果板或正式多 trajectory 分析。
  • 当前研究相关自动测试 183 项全部通过；本轮全仓 395 项中有 388 项在严格 默认沙箱通过，另 7 项仅因本地 HTTP 测试不能绑定 loopback 而在启动时被阻断。

截图仍然缺失： 当前受限环境启动系统 Chrome 时会在页面渲染前崩溃。静态 HTML 比较没有 受影响，但桌面和移动端截图没有生成。项目已经记录规则：同一方法连续 崩溃两次后，禁止第三次原样尝试。

哪些内容还没有真实运行

  • 新版 skill 执行提示词还在等待负责人审核，所以尚未运行 Markdown、TXT、DOCX、PDF 和粘贴文字五种输入测试。
  • 四个研究 agent 的协议和 Harness manifest 仍在等待审核，没有向 DeepSeek 发出真实研究请求。
  • Skill Contract 已批准，但完整研究使用的 EvaluationSuite 仍为 proposed， 历史 trajectory 也缺 TaskCase 和条件映射，因此不能形成覆盖结论。
  • 还没有真实生成任何 skill 修改副本，也没有真实运行原版本与修改版本的 成对测试。
  • Docker daemon 可访问，但固定研究镜像没有预装；真实 Harness 会停下来， 不自动下载镜像，也不会退回到没有隔离的本机执行。
  • 最终效果判断和人工发布审阅的数据结构已经写好，但还没有真实案例进入 这两个步骤。

记录和结果放在哪里

MVP 只使用普通文件，不使用数据库。每一种记录都有自己的目录和状态文件； 程序重启后可以扫描未完成的状态继续处理。

.skill-evolution/skills/

Skill 版本、执行、输入输出、trajectory、单 trajectory 分析和正式产品结果位置。

.skill-evolution/internal-research/corpora/

冻结的脱敏 raw Trajectory、导航索引、确定性基线和语料清单。

.skill-evolution/internal-research/batches/

Harness、双盲测、能力认证和四 Specialist 的内部追加记录。

.skill-evolution/experiment-requests/

pre-0027 兼容数据；当前多 Trajectory research 不会自动写入补证申请。

.skill-evolution/candidates/

Skill 修改副本、完整内容和程序计算的差异。

.skill-evolution/comparisons/

原版本与修改版本的成对运行计划和结果。

.skill-evolution/reviews/

交给人审阅的完整说明和最终发布决定。

.memory/

开发过程中接受的决定、遇到的问题和当前状态。

项目名词的白话解释

页面中保留了少量代码里的英文名称，含义如下。
项目中的名称 白话解释 为什么保留这个名称
Skill 告诉 agent 如何完成某类工作的说明文件和配套资源。 这是被测试、被修改和被发布的对象。
Trajectory 一次执行按时间排列的完整记录。 代码、文件和数据格式中都使用这个名称。
Replay 用相同任务再执行一次或多次。 用于观察稳定性，也用于重新测试修改方案。
Profiler 把多次执行中的时间、token、工具操作和失败整理成报告。 它只统计事实，不判断好坏。
Comparator 比较多个 HTML 的结构、内容和样式差异。 它列出差异，不给总分。
EvidenceBundle 固定下来、供分析使用的一整套只读材料。 确保不同 agent 看到同一份证据。
Candidate 对原 skill 做过修改的完整副本。 它还不是正式版本，必须先测试和人工批准。
Pi RPC Python 启动一个独立 Pi 子进程，并通过一行一条 JSON 消息通信。 每个分析 agent 都有独立进程和记录。
这个 MVP 明确没有做什么

没有数据库、没有常驻分布式任务系统、没有让 agent 自己发布 skill、 没有用一个总分决定好坏，也没有在证据不足时无限自动运行模型。

内容依据项目的 README、 架构说明、 后续计划 和 当前状态 整理。

本页只陈述已经实现、已经验证和仍待执行的内容，不代表尚未审核的提示词或 skill 能力说明已经获批。
