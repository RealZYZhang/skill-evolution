# 文档 HTML 可视化工具

## HTML 输出语言要求

生成 HTML 页面时，除以下内容可保留原文语言（英文或其他语言）外，**所有界面文字、导航、提示、统计标签和辅助说明必须使用简体中文**：

- 原文中已呈现的专业术语（如 _res judicata_、_habeas corpus_）
- 通用缩写（如 GDPR、API、JSON、HTML、CSS、URL、PDF、OCR）
- 代码片段、命令行示例
- API 名称、函数名、类名
- 文件名和路径（如 `config.yaml`、`/etc/nginx/`）
- 变量名、标识符
- 计量单位缩写（如 ms、GB、Mbps、ppm）

此规则适用于所有输出 HTML，包括本 skill 脚本生成的 HTML 及 agent 自行编写的 HTML。

## 目的

将长篇信息密集型文档转换为可访问、易于导航、可交互的 HTML 页面，保留原文证据、结构和可读性。当用户提供或描述一篇长文档，并要求以可视化、可快速扫描或基于网页的形式呈现时，使用本 skill。

## 何时使用

适用于以下场景：

- 学术论文、报告、政策文件、白皮书、手册、会议记录、技术规范或多章节文章。
- 要求将 `.md`、`.txt`、`.docx`、`.pdf` 或粘贴的文本转换为可读 HTML。
- 需要可视化摘要、章节地图、概念图、时间线、流程图、对比矩阵、仪表板或交互式阅读界面。
- 输出应为独立、静态、可移植且便于在浏览器中查看的形式。

当用户仅需要纯文本摘要、精确转录、法律认证或源文档的像素级复现时，不应使用本 skill。

## 设计原则

### 1. 优先保留原意，再考虑美化

- 不省略重要的论断、限制条件、公式、数据表格、引用、定义或约束。
- 除非重构能显著提高理解度，否则保留原始文档层级。
- 明确标记不确定的提取内容、OCR 错误、缺失的表格或含义模糊的图表。
- 将源内容与生成的解读内容分开。

### 2. 先概览，再缩放/筛选，最后按需查看细节

每个实质性输出都应提供：

- 顶层概览：标题、目的、受众、文档类型、关键统计数据和主要章节。
- 可导航的结构：目录、章节树和持久的本地导航。
- 渐进式细节：可折叠的子章节、可展开的证据、带链接的引用以及可下钻的卡片。

### 3. 针对长文档阅读优化

- 使用清晰的标题层级：一个 `h1`，有序的 `h2`/`h3` 章节，描述性标题。
- 使用短段落、仅在有助于快速扫描时才使用列表，并保持适当的间距。
- 正文行长度建议为 45-90 个字符，避免过宽的文本块。
- 长页面需提供固定或易于触及的导航。
- 当文档超过约 2000 词时，需提供搜索和高亮功能。

### 4. 使交互有意义

交互的目的是减轻认知负担，而非装饰。良好的交互包括：

- 文档内搜索。
- 章节展开/折叠。
- 锚点链接和可复制的章节链接。
- 按主题、实体、文档章节、证据类型或置信度筛选。
- 仅用于同一内容互斥视图的选项卡。
- 仅用于独立章节、用户可扫描并按需打开的折叠面板。
- 使用 `details` 展示补充材料、示例、推导过程或限制条件。

避免嵌套折叠、隐藏主要内容、不必要的动画、仅悬停控制的交互以及破坏浏览器搜索或键盘使用的交互。

### 5. 默认使用语义化、可访问的 HTML

- 使用地标元素：`header`、`nav`、`main`、`aside`、`section`、`article`、`footer`。
- 优先使用原生控件：`button`、`details`、`summary`、`table`、`figure`、`figcaption`。
- 仅当原生语义不足时添加 ARIA。
- 所有交互控件必须支持键盘访问，并具有可见的焦点状态。
- 不单独使用颜色传递信息。
- 提供足够的对比度、描述性链接文本、表格表头、替代文本或图例，以及减弱动画行为。
- 长页面需包含跳过链接。

### 6. 根据文档结构选择可视化类型

使用能够准确传达结构的最轻量级可视化方式。

| 文档类型 | 推荐的 HTML 可视化 |
| --- | --- |
| 层级式报告 | 固定目录、章节卡片、可折叠子章节 |
| 论证型文章或论文 | 论断-证据图、假设、局限性、引用的支撑 |
| 文献综述 | 证据矩阵、概念分类、方法/结果对比表 |
| 政策或法规 | 需求表、义务矩阵、定义、决策树 |
| 会议记录 | 时间线、决策记录、行动项看板、负责人/状态筛选 |
| 技术规范 | 架构图、API 表、数据模型、依赖关系图 |
| 流程文档 | 步骤指示器、流程图、角色/职责矩阵 |
| 数据密集报告 | 摘要指标、表格、图表、下钻说明 |
| 多方利益相关者文档 | 利益相关者地图、关注点矩阵、术语表、常见问题 |

### 7. 优先使用静态、可移植的输出

默认生成单个自包含的 HTML 文件，内嵌 CSS 和少量原生 JavaScript。除非用户明确要求或工件需要特定库，否则避免使用外部 CDN。

## 处理流程

### 阶段 0：仅在必要时明确约束

如果用户未指定，则推断合理的默认值。仅当选择会实质性影响输出结果时才提问，例如保密数据处理、目标受众、所需的视觉风格或是否允许外部库。

默认假设：

- 输出：单个自包含 `.html` 文件。
- 运行环境：无需服务器，无需构建步骤，可在现代浏览器的本地环境运行。
- 可访问性目标：WCAG 2.2 AA 精神，原生 HTML 语义，键盘可用。
- 视觉风格：克制的学术/专业风格。
- 交互程度：搜索、目录、可折叠细节、锚点链接。

### 阶段 1：输入与提取

1. 识别输入类型：粘贴文本、Markdown、TXT、DOCX、PDF、HTML 或混合文件。
2. 提取文本和结构。
3. 尽可能保留页码、标题、图注、脚注、表格、公式、引用和图片引用。
4. 对于扫描版 PDF，说明 OCR 质量可能影响准确性。
5. 规范化空白字符、标题级别、列表标记、表格边界和引用标记。

提取建议：

- Markdown/TXT：直接解析标题和列表。
- DOCX：尽可能保留标题、表格、脚注和样式。
- PDF：先提取可选文本，必要时使用 OCR。
- HTML：清理并保留语义结构。

### 阶段 2：结构分析

创建中间表示，包含：

- 文档元数据：标题、来源类型、日期（若有）、作者（若有）。
- 标题树。
- 章节摘要。
- 关键术语和定义。
- 论断、证据、假设、局限性和建议。
- 表格和图表。
- 引用和参考文献。
- 实体：人员、组织、地点、数据集、方法、技术、日期。
- 潜在的可视化模式。

一个有用的中间 JSON 结构示例：

```json
{
  "title": "文档标题",
  "metadata": {
    "source_type": "pdf|docx|md|txt|html|pasted",
    "audience": "general|technical|academic|executive",
    "word_count": 0
  },
  "sections": [
    {
      "id": "sec-1",
      "level": 2,
      "title": "章节标题",
      "summary": "一句话摘要。",
      "body_html": "<p>...</p>",
      "key_points": [],
      "claims": [],
      "citations": [],
      "children": []
    }
  ],
  "visuals": {
    "timeline": [],
    "matrix": [],
    "concepts": [],
    "process_steps": []
  }
}
```

### 阶段 3：信息架构

按以下顺序构建页面：

1. 跳过链接。
2. 页眉：标题、副标题、来源元数据、生成时间戳。
3. 概览面板：文档统计数据和主要结论。
4. 持久导航：搜索框、目录、当前章节指示器。
5. 主阅读区：章节卡片。
6. 按需展示元素：源文档摘录、证据、注意事项、定义、公式、表格注释。
7. 可视化面板：时间线、矩阵、流程图或概念图（如果源文档支持）。
8. 页脚：提取说明、局限性和生成元数据。

### 阶段 4：组件选择

默认使用以下组件：

- `DocumentShell`：页面布局、CSS 变量、响应式网格。
- `SkipLink`：跳转到主内容。
- `OverviewCards`：字数、阅读时间、章节数、主要实体。
- `SearchBox`：过滤可见章节并高亮匹配项。
- `StickyTOC`：标题树与锚点。
- `SectionCard`：章节摘要、内容、关键点和控件。
- `EvidenceBlock`：论断、支撑、注意事项、来源指针。
- `DefinitionList`：术语表。
- `ResponsiveTable`：带标题和表头范围的可滚动表格。
- `Timeline`：仅包含明确日期的事件。
- `Matrix`：比较实体、方法、数据集、需求或建议。
- `DetailsPanel`：使用原生的 `details` 和 `summary` 元素。

### Phase 5: HTML generation

生成干净、静态的 HTML：

- 转义用户提供的文本。
- 净化任何源 HTML。
- 生成稳定的锚点 ID。
- 使用语义地标。
- 将 CSS 保持在 `<style>` 块中，除非用户要求单独的文件。
- 保持 JavaScript 简洁、透明且可选。
- HTML 在禁用 JavaScript 时仍可读。
- 优先使用原生 `details` 展开方式，而非自定义折叠代码。

### 阶段 6: 验证

交付前检查：

- 标题顺序有效。
- 所有目录锚点都能正确解析。
- 交互控件可通过键盘访问。
- 搜索不会永久隐藏内容，且提供重置选项。
- 表格包含标题和尽可能多的表头单元格。
- 可视化没有引入不当的论断。
- 避免过长的行和密集的文本块。
- 避免外部网络依赖，除非获得明确许可。
- 不将敏感或机密源文本发送给第三方服务。

## 实现说明

最小实现可以使用 Python 加静态 HTML 模板编写。对于更丰富的输出，可使用 Pandoc、Eleventy、Astro 或 Observable Framework 等构建系统，但核心 skill 应保持与框架无关。

推荐的默认堆栈：

- 使用 Python 标准库从 `.md` 和 `.txt` 中提取。
- 当可用时，使用 Pandoc 进行 `.docx`、`.md` 和 `.html` 转换。
- 仅当源文档包含可选文本时，才提取 PDF 文本。
- 使用原生 HTML/CSS/JS 构建最终工件。

## 代理使用模式

使用此 skill 时，在内部遵循以下 prompt 模式：

1. "提取文档结构，不要过度概括细节。"
2. "识别文档的主要信息模式：层级、论断、流程、时间线、矩阵或数据报告。"
3. "设计最小的交互式 HTML 界面，以改善阅读和导航。"
4. "生成语义可访问的 HTML，保留源文档的章节结构。"
5. "交付前对照验收清单进行验证。"

## 输出规范

返回：

1. 一个 `.html` 文件或包含 HTML 和资源的压缩文件。
2. 对所使用的可视化策略的简短描述。
3. 已知限制列表，包括提取不确定性。
4. 验证清单摘要。

## 验收清单

- 不仅从概览就能理解文档，且不会丢失访问完整细节的途径。
- 用户可以通过标题、搜索和滚动位置进行导航。
- 章节在视觉上清晰且语义结构良好。
- 证据、注意事项、定义和表格保持可追溯到源文档。
- 页面在没有服务器的情况下也能工作。
- 页面可通过键盘操作。
- 页面在移动设备和桌面设备上都可读。
- HTML 不包含不必要的外部依赖。
- 输出诚实地反映了不确定性和缺失数据。

## 常见故障模式

- 产生一个漂亮的页面，但移除了太多内容。
- 压平标题层级。
- 隐藏重要内容。
- 根据非结构化文本创建图表。
- 使用颜色作为状态或类别的唯一指示器。
- 添加键盘无法操作的交互。
- 依赖外部脚本使文件脱机工作。
- 将 OCR 输出当作精确的源文本。
